# 첫 도장 문 개방·연속 전진 수정 — 2026-11-18

`emergency`에서 문을 여는 동안의 실내 접근, 문틀 통과, 외부 감속과 다음 배경 연결을 하나의 위치·속도 상태로 이어지게 수정했다. 기존 도트 이미지, 재질, 레이어 배치, Gameplay 씬, 판정·진행도 계산, 음악 페이즈 계산, 레인·노트·HUD는 이번 작업에서 변경하지 않았다. 이미 존재하던 작업 트리 변경은 유지했다.

## 원인과 변경

- 기존에는 성과 85% 도달 시 접근용 `SmoothDamp`를 버리고 0.10초 대기 + 0.78초 위치 곡선을 새로 시작했다. 접근 중 속도가 갑자기 사라지고 곧바로 빠른 전진이 발생했다. `travelVelocity`를 계속 유지하는 이동으로 교체했다.
- 문짝은 서로 조금 다른 감쇠 시간과 속도 제한을 사용한다. 실제 양쪽 개방이 94%에 도달한 뒤 0.30초 여유를 두며, 실내 접근은 그동안 계속된다. 약 0.85초 동안 전진 목표와 속도 상한을 연결하고, 통과 구간은 일정한 속도를 유지하다 목적지 근처에서 감속한다.
- 기존 원근 카메라와 전경 기둥(z=5.2), 문틀(z=8), 원경(z=46)을 유지했다. 이미지 전체의 스케일 변경이나 이동 중 FOV 변경은 추가하지 않았다. 가까운 문틀이 화면 양옆을 먼저 지나가고 원경은 천천히 움직인다.
- 외부에서 충분히 감속한 뒤 0.55초 여운을 확보한다. 음악상 다음 페이즈에 도달했으면 이후 1.6초 동안 배경만 부드럽게 연결한다. 기존 0.7초 강제 교체로 퇴장 중인 화면을 잘라내지 않는다.
- 첫 페이즈의 문 목표는 기존 성과 비율을 따른다. 성과가 부족한 채 곡의 페이즈 경계에 도달하면 **별도의 시간 기반 퇴장 동작**이 남은 문을 열고 같은 통과 경로를 이어간다. 이 동작은 성과를 올리거나 성공 판정을 만들지 않는다. `ActivePhase`는 계속 기존 음악 시간에 맞춰 바뀌며, 화면의 퇴장 마무리만 경계 뒤까지 이어질 수 있다.
- 시각 적분은 1/120초 이하의 단계로 처리하고 한 업데이트의 이동 시간은 최대 0.1초로 제한한다. 큰 시계 보정이나 프레임 지연으로 화면이 문 밖으로 한 번에 이동하지 않는다. 일시정지·재개 대기·재시작 동작을 유지한다.

## 미리보기

기존 `Capture Dojo Room Motion`은 합성 진행도를 사용한 24fps·120프레임, 5초짜리 오프스크린 렌더였다. 이번에는 저장된 Gameplay에서 도장만 별도 PreviewScene으로 복제해 정상 성과와 성과 0의 시간 기반 퇴장을 각각 30fps·480프레임, 16초로 촬영했다. 매 프레임 두 번의 1/60초 런타임 업데이트를 수행한다. 최종 영상은 Unity 렌더이며 이미지 사이 보간으로 만든 영상이 아니다. 실제 곡의 전체 플레이 녹화와는 구분한다.

- [성과 부족 시 퇴장 영상](../Docs/verification-images/dojo-passage-timed-exit.mp4) — 3.27초부터 음악 경계에 해당하는 퇴장 요청, 성과는 끝까지 0
- [여섯 시점 연속 프레임](../Docs/verification-images/dojo-passage-sequence.png)

정상 미리보기에서 문 개방 시작 1.67초, 충분한 개방 4.17초, 전진 가속 5.07초, 문틀이 양옆을 지나는 6.27초, 외부 시야가 확장되는 6.87초, 감속한 외부 구도 10.57초를 비교했다. 물리적인 문틀 평면 z=8 통과는 8.80초다. 근거리 레이어가 시야를 벗어나므로 화면은 이보다 먼저 외부로 열린다. 두 영상의 최고 전진 속도는 약 1.7913 단위/초이며 위치가 뒤로 튀지 않는다. 두 MP4 모두 960×540, 30fps, 480프레임, 16초를 확인했고 전체 디코딩에서 검은 구간이나 오류가 없었다.

최초 확장 캡처는 저장 씬의 `ExecuteAlways` viewport가 캡처 타깃을 바꿔 검게 나왔다. 별도 복제 씬으로 격리해 수정한 뒤 모든 프레임과 MP4를 교체했다. 재촬영 CLI 요청은 55초 제한으로 시간 초과를 반환했지만 Unity 렌더는 계속 완료됐다. [완료 로그](dojo-passage/capture-completed.txt), 960개 PNG와 두 CSV, 전체 MP4 디코딩으로 완료를 확인했다. 도장 미리보기 객체가 남아 있지 않으며 사용자의 ModeSelection 편집 화면을 유지했다.

## 검증

Unity 6000.3.23f1에서 재컴파일 후 관련 PlayMode, 기존 진행도 검사와 Smoke를 순차 실행했다. 임계치 진입 시 속도 보존, 최대 속도·가속도, 30/60/120fps 동선 일치, 프레임 지연, 성과 0의 경계 전환, 정지·재개·재시작, 배경 알파의 연속성, 기존 레인 카메라와 고정 구성 유지가 통과했다. 전체 테스트나 Player 빌드는 실행하지 않았다.

| 범위 | 결과 | 근거 |
| --- | --- | --- |
| 도장 PlayMode | 두 사례 모두 최종 통과 | [최초 실행](dojo-passage/tests-first.json), [실패 사례 재실행](dojo-passage/tests-retry.json) |
| 기존 진행도·페이즈 규칙 | 9 passed, 0 failed/skipped/inconclusive | [결과](dojo-passage/progress-tests.json) |
| Smoke | 5 passed, 0 failed/skipped/inconclusive | [결과](dojo-passage/smoke-tests.json) |

최초 도장 실행에서는 정상 퇴장을 이미 마친 시점에도 경계 후 배경 알파가 정확히 1이어야 한다는 새 검사의 기대값이 실패했다. 1.6초 연결의 초반 알파 0.98395는 의도한 동작이므로 해당 시점은 0.98 초과로 검증하고, 모든 프레임의 알파 변화량 제한은 그대로 유지했다. 해당 사례를 재실행해 통과했다. 위 결과는 최초 실행과 해당 사례 재실행을 합친 근거이며 최종 단일 전체 실행으로 표현하지 않는다.

수정 파일은 `DojoRoomPhaseView`, `GameplayBackgroundDirector`, `GameplayBackgroundPreview`, `DojoBackgroundFlowTests`와 검증 산출물이다. 새 고정 구성이나 에셋 변경이 없어 씬 재생성은 필요하지 않았다. 로컬 `main`에 아직 없는 도장 클래스는 대응하는 `main`의 `DojoEntranceView`, `PixelGameplayStyle`, `ResultsPreview`, `GameplayFlowTests` 패턴을 읽고 작업했다.
